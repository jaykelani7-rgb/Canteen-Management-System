# Hosting decision and account setup

Research checked on 9 October 2026 against official provider documentation. No cloud resource, paid subscription, DNS change, deployment or public HTTPS endpoint was created by this work. Dollar amounts are USD before taxes, currency conversion, domain registration, payment fees and optional SMTP/Gemini usage. Recheck the provider order summary before approving expenditure.

## Free staging first: 40–50 testers

For the immediate testing group, recommend **Render Free FastAPI + Neon Free PostgreSQL + account-owned Upstash Free Redis**, all in Singapore where the free dashboard offers it. The API gets a persistent `https://<service-name>.onrender.com` address with managed TLS; it is not a quick tunnel. Frontends can be built locally and hosted separately. Expected infrastructure spend is **$0 only while every service stays on its Free plan and within quotas**. This is a controlled staging pilot, not an always-on production guarantee or a certified 500-user capacity claim. User count alone does not predict throughput: menu polling, order tracking and attendance concurrency drive resource usage.

Render Free blocks SMTP ports 25/465/587, so the current SMTP recovery implementation must remain disabled for this pilot; do not present unavailable email recovery as working. Render explicitly advises against Free instances for production. Upstash [resource-inactivity terms](https://upstash.com/trust/terms) permit deletion of a Free resource after one week without requests; monitor provider notices. Do not use its anonymous 72-hour scratch-database endpoint. Neon/Upstash account-owned Free resources remove the temporary-URL problem but do not create an uptime SLA. Review current provider terms during signup rather than assuming all free services have identical commercial/support policies.

Use `/api/health` for the Render liveness health check and call `/api/ready` manually before tests and after deployment. Continuous readiness checks can prevent Neon's scale-to-zero and consume its compute allocation. A deliberate start-of-session check is different from a perpetual keep-awake service. Do not add a cron merely to circumvent Render idle-sleep policy.

### Exact free account/setup steps

1. Create account-owned projects at [Neon](https://console.neon.tech), [Upstash](https://console.upstash.com) and [Render](https://dashboard.render.com). Enable MFA. Choose **Free** explicitly. Do not upgrade, add billable resources or enter a credit card to lift quotas without approval. Neon requires no card for Free. Upstash states that adding a card upgrades Free to pay-as-you-go. Render's account/anti-abuse verification may vary; if it requests a paid plan or billing authorization, stop and report that requirement rather than promise universal card-free onboarding.
2. In Neon create `canteen-staging`, choose **PostgreSQL 16** and **AWS Singapore** if currently offered, database `canteen_staging`. Use a small compute setting within Free. Copy the **direct TLS connection** privately for backup/migration operators and a separate least-privilege application's TLS connection into managed secrets. Do not paste connection strings in chat. Preserve the original local database; restore a verified backup into this new empty destination and check revision/counts before additive migrations. A data sample may be sanitized for testers, but never modify the original data to achieve this.
3. In Upstash Redis → Create Database enter `canteen-staging`, primary **Singapore**, no extra read replicas; select **Free**. Copy the TCP Redis TLS URL/port/password from its Details connection area into server `REDIS_URL`; do not use the REST URL with redis-py, disable TLS verification, or put this secret into Vite/Android configuration. Check provider console usage throughout testing.
4. Build the backend image from the complete current local source, **linux/amd64**, using `backend/Dockerfile` with repository-root context. Publish it to an owner-controlled registry only after owner authentication and explicit publication approval; use a private Docker Hub/GHCR repository and restricted pull credential. This is an image upload, not a Git commit/push. Keep image layers free of `.env`, dumps, local credentials and payment secrets. Do not deploy an old GitHub checkout that omits the current uncommitted implementation.
5. Render → New → **Web Service** → **Existing Image**. Enter the actual image digest URL and, for a private image, add the registry name/username/read-only token directly in Render. Set name `canteen-staging-api`, region **Singapore**, compute **Free**, health check `/api/health`. Supply the prepared safe start command from deployment documentation; it must bind `0.0.0.0` on Render's `$PORT`. Free services lack pre-deploy commands and shell jobs, so apply reviewed migrations from the authorized local migration runner before starting the API. Runtime refuses a schema revision mismatch.
6. In Render Environment set the values from the staging configuration template directly: exact `ENVIRONMENT`, role CORS origins, native origin `https://localhost`, `DATABASE_URL`, `REDIS_URL`, random JWT secret, disabled demo/bootstrap/payment/recovery flags and exact public host allowlist. Supply secrets in Render only. Use staging protection equivalent to production. Keep application and migration DB roles separate; the API must never run with the schema owner's credentials.
7. Deploy the Free image and read the generated real `onrender.com` URL from the dashboard. Wait through cold startup. Verify its external HTTPS `/api/health` and `/api/ready` from the owner's machine/phone. Only then provide that **public URL without secrets** for Android rebuilding. No `.example` URL, localhost backend or quick-tunnel URL belongs in the rebuilt release frontend.
8. Student and Admin browser origins must use the same backend and need verified CORS/cookie settings. Free static hosts with unrelated provider hostnames can conflict with existing cookie same-site rules. Keep existing PWA/Admin during backend pilot unless the reviewed host/proxy configuration is also deployed. To upload the current built static files without a Git push, a static host supporting artifact upload can be selected after owner login; this is a separate reviewed deployment step, not proof that both web origins are already hosted.
9. Run the 40–50 tester pilot after one-person staging acceptance: login, menu, order creation, persisted history/tracking, admin status, mess attendance and network/expired-session behavior. Use disabled real payments or verified provider sandbox credentials; never fake captured payments. Record latency/concurrency, errors and provider quota usage before approving the 500-user move.

Render officially supports [prebuilt public/private registry images](https://render.com/docs/deploying-an-image); this path preserves the no-Git-push instruction. A private registry account/token and permission to upload the source-containing image are prerequisites, not credentials to send through chat. Free database quota/backup limitations and cold starts remain even after a stable HTTPS URL is issued.

## Paid production recommendation: approximately 500 students later

For one college and an operator who can maintain Linux/PostgreSQL, use the existing Docker Compose/Caddy stack on a DigitalOcean Basic Droplet in Bangalore (`blr1`), or Singapore (`sgp1`) if the selected plan is unavailable. Run one FastAPI service, private PostgreSQL 16, private Redis 7 and the existing two static frontends. Caddy terminates HTTPS; the Android app uses a dedicated API hostname. This is an operator-managed database architecture, not a managed PostgreSQL service.

The lowest predictable India-region starting budget is **$19.40/month**: $12 for 2 GiB RAM/1 vCPU/50 GiB disk, $2.40 weekly VM backups, and $5 Spaces storage for encrypted database backups. This is a measured pilot starting size, not a verified lunch-break capacity guarantee. Build images away from the small production VM. For launch with unmeasured concurrency, prefer 4 GiB/2 vCPU: **$33.80/month** including the same backup layers. These totals are arithmetic from [Droplet pricing](https://www.digitalocean.com/pricing/droplets), [weekly backup pricing](https://docs.digitalocean.com/products/backups/details/pricing/) and [Spaces pricing](https://www.digitalocean.com/pricing/spaces-object-storage). DigitalOcean lists both [Bangalore and Singapore regions](https://docs.digitalocean.com/platform/regional-availability/); measure latency from campus before selecting one.

A VPS is suitable only with an assigned operator, patched host, monitoring, successful restore rehearsal and an accepted outage/recovery policy. One host remains a single failure point. If the college cannot provide an operator, choose a managed platform rather than treating the VPS price as the complete operational cost.

## Separate staging and production

Use separate hosts/projects, DNS names, database credentials/data volumes, Redis instances and JWT secrets. Staging is for sanitized data and provider sandbox credentials; it never shares live tables or payment credentials. Both Student and Admin use the same API/database within their environment. Start staging only during validation if budget requires; do not sleep the production API during canteen service.

Budget example: 2 GiB production with weekly VM backups and Spaces plus one continuously running 2 GiB staging host is **$31.40/month**, before any extra staging VM backups. The $5 Spaces allowance can hold segregated encrypted backup prefixes for both environments; choose an off-host region and restrict credentials per prefix/bucket. Full independent account/region redundancy costs extra. A stopped VPS may still incur charges; inspect provider billing rather than assuming shutdown cancels cost.

Keep Student PWA and Admin on their existing separate hosts/origins. For managed alternatives, use sibling custom hostnames under the owned domain if browser cookie mode requires same-site cookies; unrelated provider frontend/API domains can otherwise require reviewed cookie configuration. Android uses Bearer authentication and its packaged origin is not a backend address. CORS must list exact allowed web and native origins, as documented in the deployment/security guide.

## Account setup required after cost approval

The following are instructions for the owner; resource creation is billable. No step has been executed against a provider account.

1. Open [DigitalOcean](https://cloud.digitalocean.com/), create the college-owned account/team, enable MFA, configure billing and monthly spend alerts. Approve the production/staging budget before clicking Create on any paid resource. No access token/password needs to be pasted into chat.
2. Create a project named `canteen-production`. In Create → Droplets select **Ubuntu 24.04 LTS**, **Basic**, **Regular**, **2 GiB / 1 vCPU / 50 GiB ($12/month)** for a measured pilot or **4 GiB / 2 vCPU / 80 GiB ($24/month)** for additional headroom. Select **Bangalore BLR1**, or **Singapore SGP1** if unavailable. Choose SSH-key authentication, add only the public key, set hostname `canteen-production`, enable monitoring and weekly backups. Keep the private key on the owner's machine.
3. Add a Cloud Firewall: inbound TCP80/443 from internet; TCP22 from the operator's public IP only; optional UDP443 for Caddy HTTP/3. Do not open PostgreSQL5432, Redis6379 or backend8000 publicly. Attach it to the Droplet. Restrict outbound as deployment dependencies allow.
4. Use a domain the college owns. Create DNS A records for the actual Student, Admin and API hostnames pointing to the Droplet IPv4. Configure AAAA only if the server's IPv6 routing/firewall is verified. Set those real hostnames in private deployment configuration. Domain registration is an additional registrar-specific cost; do not purchase one automatically.
5. Create a **private** Spaces bucket after approving the $5/month service, in a different appropriate region from the VM. Configure restricted backup credentials directly in the operator's private secret store, encryption, retention and restore testing. Keep public file listing/CDN access disabled for database backups. Provider VM backup is only the second recovery layer.
6. Prepare `/secure/canteen/` host files owned by the deployment operator with restrictive permissions. Supply the backend variables listed in `deployment/PRODUCTION.md` and the configuration template, plus separate elevated migration credentials. Set each environment's exact origins and API hostname. Never copy local development `.env` wholesale into production or expose database/JWT/payment/SMTP/Gemini secrets in chat, Git, APK or static frontend variables.
7. Upload/build the current reviewed source or container artifact without committing/pushing. Follow the deployment guide's backup → empty target restore → validation → additive migrations → API readiness → DNS/TLS sequence. A new hosting destination is not permission to reset existing data. Keep the original database unchanged until the owner accepts a verified cutover.
8. Create `canteen-staging` as a separate project/host with independent configuration and sanitized data. Configure sandbox payment credentials only after real provider verification. Keep payment/recovery features disabled when required server credentials/delivery are absent.
9. Verify public `/api/health` and `/api/ready` over the issued HTTPS hostname from outside the host. Then test login/menu/order/history in staging, make the Android build point to the verified real URL, and repeat tests on the owner's installed phone. A browser or local health check does not establish public deployment success.

If choosing Railway instead: approve Pro and spend alerts, create distinct production/staging environments, add PostgreSQL and Redis services in Singapore with persistent volumes, enable scheduled backups/PITR, configure private service references and elevated migration credentials separately, deploy the root-context backend Dockerfile, set the documented start command and `/api/ready` health check, disable Serverless, then generate the API's HTTPS domain in Settings → Networking. Supply secrets directly in provider variables. A permanent provider domain avoids purchasing a domain for Android initially; separate PWA/Admin cookie origins still need verified configuration. Deployment of the current uncommitted state can use the provider CLI/container artifact rather than pushing an incomplete GitHub checkout.

## Approval and deployment boundary

The owner must choose hosting, approve recurring costs, create/login to the account and provide the actual domain/host configuration through the provider or private filesystem. Only a public HTTPS endpoint with successful externally fetched health/readiness can be reported as deployed. Until that exists, the installed placeholder APK cannot complete login or ordering; it needs a rebuilt bundle after configuration. Preparation, cost research and local tests do not substitute for the public endpoint or physical-phone end-to-end tests.
